# The code, then and now

A walkthrough of the rebuilt announcements dashboard (commit `75aac04`) set against the 2018
original ([markmc27/UmbracoPushNotifications](https://github.com/markmc27/UmbracoPushNotifications),
Umbraco 7.12.3). Written to help explain the code in the 24 Days article.

## Summary

- **Same feature, almost entirely different Umbraco code.** Every Umbraco-facing piece was
  replaced: `Dashboard.config` became a JSON manifest, AngularJS became Lit and TypeScript, the
  authorised JSON controller became a Management API controller, PetaPoco statics became
  repositories, and "create the table if missing" became a versioned migration plan.
- **The web platform code barely moved.** The service worker is still about 40 lines with the
  same `push` and `notificationclick` handlers, the payload is still `{ title, message, url }`,
  and the server still uses the same `WebPush` NuGet library.
- **Roughly twice the hand-written code (about 1,700 lines against about 750), plus 320 lines
  of tests where 2018 had none.** The extra lines are not ceremony for its own sake: they buy
  validation, error handling, server-side authorisation, accessibility and testability that the
  2018 version did not have.
- **The 2018 secrets problem is gone by design:** no keys or tokens in source control, and the
  site refuses to start without them.

## Walkthrough, layer by layer

### 1. Registration and start-up

**2018.** Two mechanisms. `config/Dashboard.config` added an "Announcements" tab to the Content
dashboard and denied it to translators. A `RegisterEvents : ApplicationEventHandler` checked on
every start whether the `PushSubscriptions` table existed, and created it if not.

**2026.** Also two, but both declarative and owned by the extension:

- `Composers/AnnouncementsComposer.cs` registers everything with dependency injection: options
  (validated at start-up), repositories, the push sender through `IHttpClientFactory`, the push
  service, the rate limiter, the authorisation policy and the announcement service.
  `Program.cs` is untouched.
- `Client/public/umbraco-package.json` registers the dashboard with two conditions, which read
  almost like the old XML:

  ```json
  { "alias": "Umb.Condition.SectionAlias", "match": "Umb.Section.Content" },
  { "alias": "Umb.Condition.CurrentUser.GroupId", "noneOf": ["f2012e4c-d232-4bd1-8eae-4384032d97d8"] }
  ```

  That GUID is Umbraco's built-in Translators group key, confirmed from the 17.8.2 packages. The
  design had guessed a different value; checking the installed package rather than trusting
  memory caught it.

**Talking point:** the old `<deny>translator</deny>` and the new `noneOf` express the same rule.
What changed is that the extension now carries its own registration, so it can be packaged.

### 2. Backoffice UI: AngularJS to Lit

**2018.** `CommunicationDashboardController` (AngularJS) loaded the count and history through a
hand-written `communicationResource` (`$http.get("backoffice/Communication/Communication/GetHistory")`),
and opened an `umb-overlay position="right"` with `umb-toggle` switches for Email, Push and Facebook.
It also posted to Facebook from the browser with a hard-coded page access token.

**2026.**

- `dashboard/announcements-dashboard.element.ts`: a Lit element extending `UmbLitElement`. It
  loads the count and history in parallel, shows loading bars, an empty state and an error state,
  and renders a `uui-table`. Edit links go to the document workspace by **page key**
  (`section/content/workspace/document/edit/{key}`), because the new backoffice routes by key,
  not integer id.
- `modal/add-announcement.modal-token.ts`: a modal token with `type: "sidebar"`, the direct
  successor to the right-hand overlay.
- `modal/add-announcement.modal-element.ts`: the form. It validates the short name and heading,
  moves focus to the first problem, shows a busy state, blocks double submit, keeps the editor's
  input if the server says no, and shows a notification with "sent to N of M subscribers".
  The "What is a push notification?" text uses a native popover, so keyboard users can open it.
- `entrypoints/entrypoint.ts`: wires the generated API client into the backoffice auth context
  (`authContext.configureClient(client)`), so every call carries the backoffice bearer token.

**Talking point:** in 2018 the dashboard trusted a cookie session and string URLs. Today the
dashboard calls a typed client generated from the server's own OpenAPI document. Rename a
property on the server, regenerate, and the TypeScript compiler shows you every place that breaks.

### 3. Backoffice API

**2018.** `CommunicationController : UmbracoAuthorizedJsonController` with
`[PluginController("Communication")]`. Any logged-in backoffice user could call it, including
translators, because only the dashboard tab was hidden.

**2026.** `Controllers/AnnouncementsController.cs` derives from `ManagementApiControllerBase`:

```csharp
[BackOfficeRoute("announcements/api/v{version:apiVersion}")]
[MapToApi(Constants.ApiName)]
[Authorize(Policy = AnnouncementsAuthorization.PolicyName)]
public class AnnouncementsController : ManagementApiControllerBase
```

- **Its own Swagger document** (`Composers/AnnouncementsApiComposer.cs`), at
  `/umbraco/swagger/announcements/swagger.json`, so the generated client contains only these
  three endpoints. Operation IDs are the action names, giving short client methods such as
  `AnnouncementsService.getHistory()`.
- **Server-side authorisation** (`Authorization/AnnouncementsAuthorization.cs`): the policy
  starts from Umbraco's own Content section policy and adds a requirement that the user is not
  in the Translators group. A translator calling the API directly gets 403. The UI condition is
  now a convenience, not the only control.
- **Problem details for errors:** a missing parent or a failed publish returns 400 with a
  readable `detail`, which the sidebar shows as is.

### 4. Creating the announcement

**2018.** All in one controller action: find the folder via `ContentCache.GetByRoute("/")`,
create a `newsPage` with hard-coded aliases, `SaveAndPublishWithStatus`, then send. If the
publish failed, the method returned `-1` and the next line read node `-1`, which would most
likely throw.

**2026.** Split in two, so the rules can be tested without Umbraco:

- `Announcements/AnnouncementService.cs` holds the flow (design D5): validate, find the parent,
  create and publish, push, record. **Push only happens after a successful publish.** Page name
  and message format match 2018 exactly (`20261121-pool-closed`, `21 Nov Pool closed`).
- `Announcements/AnnouncementPages.cs` does the Umbraco work with the async
  `IContentEditingService.CreateAsync` and `IContentPublishingService.PublishAsync` that came with
  the new backoffice. It also refuses to push if the page has no absolute URL.
- `Announcements/ContentModelOptions.cs`: the doc type and property aliases come from
  configuration, validated at start-up, instead of being hard-coded.

### 5. Push delivery

**2018.** `PushService` looped through every subscription **one at a time**, deleted 404/410
subscriptions **inside the loop**, and swallowed every other error.

**2026.**

- `Push/PushService.cs` sends with `Parallel.ForEachAsync` (four at a time by default), collects
  gone endpoints and deletes them **after** the loop, logs other failures with the status code,
  and returns a `PushSendResult(Attempted, Succeeded, Failed, Removed)`.
- `Push/WebPushSender.cs` is the only class that touches the `WebPush` library. It turns the
  library's exceptions into a status code. That seam is what lets the tests use a fake sender.
- `Push/PushOptions.cs`: title, icon, concurrency and VAPID keys, validated at start-up with
  messages that say how to fix them ("Generate keys with: npx web-push generate-vapid-keys").

The payload is the 2018 shape plus an `icon`, so the service worker no longer hard-codes one.

### 6. Persistence

**2018.** A static `PushSubsciptions` class using `ApplicationContext.Current.DatabaseContext`,
a POCO, and a JSON file for history. The table was created at start-up if missing.

**2026.**

- `Persistence/PushSubscriptionDto.cs` and `AnnouncementHistoryDto.cs`: NPoco DTOs (NPoco is
  PetaPoco's descendant, so the attributes look familiar). The endpoint has a unique index.
- `PushSubscriptionRepository` and `AnnouncementHistoryRepository`: injected, using Umbraco's
  `IScopeProvider` for transactions. Subscribing again with the same endpoint updates the keys
  instead of adding a duplicate row (2018 added a new row each time).
- `Migrations/AnnouncementsMigrationPlan.cs` (a `PackageMigrationPlan`) runs
  `CreateAnnouncementsTables` once, records that it ran, and shows in the backoffice Packages
  section. Future schema changes become new steps in the plan.
- The SQL sits in small internal query classes, so the tests run it against an in-memory SQLite
  database without booting Umbraco.

### 7. The public subscribe endpoint

**2018.** `PushController : UmbracoApiController`, form fields, a `cookieToken:formToken` string
split by hand and passed to `System.Web` `AntiForgery.Validate`, and a custom `ThrottleAttribute`
(one call per IP per hour).

**2026.** `Subscriptions/PushSubscriptionsController.cs` is a plain ASP.NET Core controller. Each
concern is now a built-in attribute:

```csharp
[HttpPost]
[ValidateAntiForgeryToken]
[EnableRateLimiting(SubscribeRateLimiting.PolicyName)]
public async Task<IActionResult> Post([FromBody] PushSubscriptionRequest request)
```

- The request model uses data annotations (`[Required]`, `[Url]`, `[MaxLength]`), so bad input
  gets a 400 before the action runs.
- `Subscriptions/SubscribeRateLimiting.cs` uses ASP.NET Core's rate limiter (five calls per IP per
  hour by default) and adds the middleware through an `UmbracoPipelineFilter`, again leaving
  `Program.cs` alone. Development settings shorten the window to one minute for testing.

### 8. The site front end

**2018.** `pushModule.js` (jQuery, IIFE module) and `sw.js` at the root.

**2026.**

- `Client/src/push.ts`: the same journey without jQuery. It checks for a secure context and
  support, registers `/sw.js`, hides the button if this browser is already subscribed, and posts
  `JSON.stringify(subscription)` with the antiforgery token in a header. If the server rejects the
  subscription, it unsubscribes the browser again, so the visitor is offered the button next time.
  Status messages are announced to screen readers.
- `Client/src/sw.ts`: nearly line for line the 2018 file, now typed against the WebWorker library.
  The icon comes from the payload as an absolute path (2018's relative path broke on sub-pages).
- `Client/vite.config.ts` builds both into `wwwroot` with fixed names: `/sw.js` must not get a
  content hash, or each build would register a new service worker.
- `Views/layout.cshtml` renders the antiforgery token and VAPID public key into `<meta>` tags.

### 9. Building it

`build/ClientBuild.targets` is shared by both projects. Before the .NET build it runs `npm ci`
(only when `node_modules` is missing) and `npm run build` (only when `Client/` changed), so
`dotnet build` works from a fresh clone. The built JavaScript is gitignored. 2018 used Gulp,
run separately.

### 10. Tests

2018 had none. Now there are 20 xUnit tests:

- `Push/PushServiceTests.cs`: all succeed; the mixed case (4 attempted, 2 ok, 1 failed,
  1 removed); 404 counts as gone like 410; no response is a failure and the subscription is kept;
  no subscribers; the payload carries the configured title, message, URL and icon.
- `Announcements/AnnouncementServiceTests.cs`: page naming, message format, the happy path
  (page, push to its URL, history row), required fields checked first, a missing parent creates
  and sends nothing, and a failed publish sends nothing.
- `Persistence/RepositoryQueryTests.cs`: the real SQL against in-memory SQLite: the upsert,
  counting, deleting by endpoints, and history newest first.

The end-to-end run used Playwright for everything except clicking the OS notification. In
Playwright's Chromium on Windows the click was dropped, so it was checked in the human's own
browser instead (see the build log, task 8.2).

## What did not change

- The Push API, VAPID, the service worker events and the payload shape.
- The `WebPush` .NET library (1.0.11 then, 1.0.13 now).
- The behaviour editors see: a Content dashboard tab, a count, a history table, a right-hand
  panel with short name, heading and text, a published page, a push to everyone.
- Exact-match click handling: the service worker focuses a tab only if its URL is identical.

## Worth knowing (from reading the code)

None of these block the PoC; they are honest notes for the article or a follow-up.

- **Sending still happens inside the HTTP request.** Parallel sends make it fast for a small
  club, but a large list would keep the editor waiting. Background sending is the first deferred
  improvement.
- **History is written after the push.** If that insert failed, the notifications would have gone
  out with no history row. Unlikely, but a background job with its own record would fix it.
- **Two simultaneous subscribes for the same endpoint** could race past the "does it exist?"
  check; the unique index would then reject the second with a server error. Harmless in
  practice.
- **Finding the parent** uses the older synchronous `IContentService.GetPagedOfType`, alongside
  the newer async editing services. It works; it is just a mix of styles.
- **The 1,572-line generated client** is committed. That is the template's convention, and it
  means the dashboard builds without the site running, but it needs regenerating after any API
  change.

## Possible talking points for the article

1. "The Umbraco code was rewritten; the web platform code was copied." The contrast between the
   backoffice and the service worker is the clearest picture of eight years of change.
2. Server-side authorisation: the old dashboard hid a tab; the new one closes the door.
3. Generated, typed API clients replace hand-written `$http` calls.
4. Built-in ASP.NET Core features (rate limiting, antiforgery, options validation) replace
   hand-rolled ones.
5. More lines, but each one earns its place, and every rule now has a test.
